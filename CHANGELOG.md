# Changelog

## Unreleased

First public development version.

- Added: an opt-in model evaluator in `tools/bench/v2` with disposable Docker environments, separate generator and decider profiles, answer-style and cost metrics, response replay, and HTML human review. Behavioral execution requires approval for each command.

- `setup` is a guided conversation. It looks at the machine first (which hosted services have their key variable set, by name only, and which local servers answer on their default port), lists the providers as local or remote with what it found, confirms a local port, asks where the key is (`env:NAME` or `file:PATH`; a pasted key is refused and never echoed), asks the server for its models to confirm the address and the key, and asks for the model name, which is never guessed. It does the same for an optional checker, listing only the ones found. A remote service needs your agreement before anything is contacted.
- Changed: `setup --yes` needs `--provider` and `--model` and no longer picks Ollama because one is running. New options: `--api-key <env:NAME|file:PATH>` (`--api-key-env` still works), `--checker`, `--checker-model`, `--checker-url`, `--checker-api-key`, and `--verify`, which asks each server for its models before anything is written. `--base-url` also works with a preset. `config init --provider` needs `--model` too.
- Plugin API: `Provider::models` and `Decider::models` list the models a server offers (the plugin knows the path, `/v1/models` for the built-ins), and `shellmate_api::parse_model_ids` reads the reply.
- Changed: `config init` without `--provider` writes a config whose provider examples are comments (a hosted model through OpenRouter, and a local one), so no provider is chosen for you. `--provider` and `--model` go together and write an active config. The commented decision model example uses OpenRouter and `~typesafe/jev-latest`.
- The `systemone` decider has a `typesafe` preset (`https://api.typesafe.ai`, key from `TYPESAFE_API_KEY`). It is for deciders only, so a provider does not accept it.
- The `systemone` decider has a `path` setting (default `/v1/systemone`), and a preset can carry its own path: `openrouter` uses OpenRouter's alpha Decisions API at `/alpha/decisions`. A custom `endpoint` never inherits a preset's path.
- `shellmate config edit` opens the config file in `$VISUAL` or `$EDITOR` (then `vi`) and runs `config check` on it when the editor closes. The editor is started directly, never through a shell.
- Changed: an `endpoint` is the base URL of the server, with no version in it, and each plugin adds its own path. The OpenAI-compatible provider posts to `/v1/chat/completions` and the `systemone` decider to `/v1/systemone`. An old `endpoint = "http://localhost:8000/v1"` must become `"http://localhost:8000"`. Presets and the `setup` prompts follow. Plugins share the preset lookup and the key rule through `shellmate_api::{PRESETS, Preset, resolve_endpoint, resolve_api_key}`, so deciders accept the same presets as providers (`openai`, `openrouter`, `ollama`, `lmstudio`, `localai`) and read the same default key variables.
- Tools are plugins: `man`, `exec` and `read` implement `shellmate_api::Tool` in `shellmate-builtin` (features `tool-man`, `tool-exec`, `tool-read`). Every `[tools.<name>]` table has `enabled`, `approval` and `preapproved`, kept by the core, and the tool's own keys. The core still enforces approval, pre-approval, taint and escaping, so a tool cannot skip them. Small changes: a failed `read` taints the turn, a `man` page is capped at 4 MiB, and `[tools.man] approval = "ask"` is refused when the engine is built.
- `ask`, `generate` and `explain` from your prompt in fish, zsh and bash, streamed as they are generated.
- Providers: OpenAI-compatible endpoints (OpenAI, OpenRouter, Ollama, LM Studio), with fallback chains.
- Privacy: context levels per provider trust, reversible secret redaction (fails closed), `--dry-run`.
- Follow-up conversations per shell session (tmpfs store), audience rule for remote providers.
- `man` tool with a classifier and policy; nothing the model asks for runs without passing both.
- The `openai` and `openrouter` presets read `OPENAI_API_KEY` / `OPENROUTER_API_KEY` when `api_key` is not set (not when a custom `endpoint` is set).
- `exec` tool (`ask` only): the model can ask to run one simple command to look at your machine. Each command needs your `y` at a prompt on the terminal (only a single key counts; earlier typeahead is flushed; no terminal means deny). A rule-based classifier rates commands, and high risk needs `yes`. `[tools.exec] preapproved` rules skip the prompt for commands the classifier does not flag; the classifier keeps its veto. Commands run directly (never through a shell) with a sanitized environment, a timeout and capped output. `config check` warns about overly broad rules.
- The config written by `setup` and `config init` binds every action: `alt+m` ask, `alt+i` generate, `alt+j` explain, `alt+k` new-conversation and capture on `alt+r` (`alt+e` in bash, where `alt+r` is taken).
- `setup` offers LocalAI and a `custom` provider: any OpenAI-compatible server, with the base URL asked for (or `--base-url`) and an optional `--api-key-env`. A loopback URL is trusted as local, any other as remote.
- Help: `shellmate --help` lists commands by category.
- Changed: `generate` is command-only. The model is told to reply with exactly one command and nothing else; shellmate shows only that command (no prose, no alternatives, no streaming). With no single command you get the model's one short sentence instead. `ask` is unchanged.
- Safety: everything typed while shellmate is working is discarded, whatever the outcome (answer, explain, error, cancel), so a key press made before the result was shown can never reach the shell. Covered by the shell conformance suite.
- `shellmate run -- <command>` runs a command as usual and keeps a bounded, private copy of its output (tmpfs, per shell session). The next request carries it at context level 2, redacted and labeled as data (`[context] capture_bytes`). The `capture` action (suggested `alt+r`) wraps the input line in `shellmate run --` and unwraps it on a second press; it calls no model and runs nothing. A request that carries captured output is tainted: `exec` pre-approvals are suspended for it (INV-4).
- Command validator: every suggestion from `ask`/`generate` is checked before it reaches the input line (parses in your shell via `-n`, programs exist in `PATH`, risk notes). Notes only: the command is always still placed. Optional semantic check (`[validator] semantic = true`) asks a decision model whether the command matches the request and how dangerous it is, and shows only findings the model is confident about. Deciders are a new plugin kind configured like providers (`[deciders.<name>]`, `builtin:systemone` for any `POST /v1/systemone` endpoint such as Ollama's decision models, Ollaya or hosted APIs); with none configured the LLM answers the same questions. Remote deciders need redaction and see only the request, the command and the shell name.
- `read` tool (`ask` only): the model can ask to read one text file from the working directory (or `[tools.read] roots`). Each file asks first and the prompt says where the text goes; `preapproved` path rules skip it. Symlinks are resolved before the check, binary files and anything credential-looking (`.env`, `.ssh`, `*.pem`, `.git/config`, ...) are refused and no rule can unlock them, and a missing path and an outside path get the same answer. File text is labeled as data, and reading it taints the rest of the request, as does command output.
- Context collectors: `project` (level 1+, kind of project from file names only) and `git` (level 2+, branch, ahead/behind, change counts), with `git_log_lines` to opt in to commit subjects (which taint the request).
- Security: git is run with `core.fsmonitor` disabled, for the collector and for approved `git` commands in the exec tool, so a cloned repository cannot execute code when git checks its working tree.
- `shellmate context`: shows, per provider, which pieces of context would be sent and why the others are held back (level, setting, or nothing to send). Sizes and reasons only; `--full` adds the redacted payload. Nothing is sent.
- `doctor` checks that each decision model (decider) is reachable and warns when `[validator] timeout` is too short for a model that has to be loaded first.
- `invoke --timings[=json]`: where the time of a request went (start-up, context, model, first text, checks, overhead, total), in microsecond precision.
- `shellmate check <line>`: the command checks (parses in your shell, programs exist, risk) on a line you give, without running it.
- Benchmark tooling in `tools/bench`: `perf.py` (process performance against a fake model, interleaved runs, memory, budgets and baseline comparison), `evals.py` (models scored by fixed rules from TOML cases, with cold start, latency and tokens per second, record and replay) and `report.py` (Markdown pages for the docs). CI runs the tooling's tests, the replay suite and the performance budgets.
- Fix: with `[ui] stream = false`, tool activity (a `man` page, a pre-approved `exec` or `read`, a refusal) was not printed, so a call covered by a rule ran silently. The engine now separates what it did from what the model said; the former is always shown.
- Secrets: `cmd:program args` as a secret reference, for keys that live in `pass`, 1Password, `age`, the system keyring or your own script (`api_key = "cmd:pass show api/openai"`). The program runs directly (never through a shell; a line with shell syntax or a relative program path is refused), with a small environment, no input, a timeout and capped output, and what it prints is the key. It is fetched when the provider is first used, not at start-up, so an unused fallback provider never runs it, and `config check` and `--dry-run` do not run it. A failure is a configuration error and does not fall back to the next provider. New `[secrets]` settings `cmd_timeout` and `pass_env`. `doctor` runs each `cmd:` secret once and reports whether it worked, `config check` warns when a key seems to be written in the line, and `config show` hides such arguments. Provider plugins get a `prepare` hook for this.
- Secrets: `keyring:service/account` reads the system keyring. It is short for the `cmd:` line of `secret-tool lookup` (Linux) or `security find-generic-password` (macOS), so it has the same limits and is fetched on first use, and it adds no dependency.
- `setup`, `doctor`, `install-shell`, `config show/init/check`, `audit`, `--explain`.
- Building from source needs Rust 1.86 or newer (`rust-version` now says so; it said 1.80, which the locked dependencies never allowed).
- `ask`: the model is told that steps that belong together go in one command block (`&&` when one needs the other) and that a second block is shown as an alternative under "Other options". With two local models, answers that put a follow-up step in its own block went from 0 of 2 to 2 of 2 on three new eval cases.
- Colour and formatting: answers, tool activity, errors, notes, the waiting indicator, `doctor` and the approval prompt are shown in colour, `check`, `config check`, `config show`, `context`, `audit`, `conversation` and `setup` are coloured too, and the markdown in answers (bold, italic, code, lists, headings, quotes, rules, fenced blocks) is formatted, when the terminal can show it. Plain text everywhere else: no terminal, `TERM=dumb`, `[ui] color = "never"`. `NO_COLOR` keeps bold and italic but removes colour; `CLICOLOR`, `CLICOLOR_FORCE` and `[ui] color = "always"` work as expected. The palette is the 16 terminal colours, so it follows your terminal theme. New settings `[ui] color` and `[ui] markdown`, and `shellmate render` to preview. The command placed in your input line is never styled, and model text can never add its own escape sequences.
- Changed: in a terminal that is not UTF-8, notices use ASCII symbols (`+`, `x`, `->`); they were always Unicode.
- Fix: a line break arriving right after the first word of an answer was dropped (`Yes.` then a blank line ran into the next paragraph).
- `SHELLMATE_TIME_SCALE` (1 to 100) stretches the short limits on git, the shell syntax check, `man` and the wait for output after a `cmd:` secret program exits, for slow disks and huge repositories.
- Fix: a `cmd:` secret whose program had already printed the key and exited could be reported as an error when a helper it left behind still held the pipes and `cmd_timeout` was shorter than the 300 ms wait for it. That wait now ends at the timeout at the latest and counts as success, and it follows `SHELLMATE_TIME_SCALE`.
- Redaction: a value after `Authorization:` is redacted whatever its length (the bearer-token rule needed 16 characters or more).
