# Update the documentation

The public docs are the Starlight site in `website/`. The top-level `docs/` folder is git-ignored internal design notes; do not edit it as if it were published, and do not link to it from the site.

## Where things are

- Pages: `website/src/content/docs/docs/{start,guides,concepts,reference,benchmarks}/` and `contributing.md`. The URL gets a `/docs` prefix.
- Sidebar: `website/astro.config.mjs`. A new page does not appear until you add `{ label, slug: 'docs/<path without extension>' }`.
- Landing page: `website/src/pages/index.astro` (plain Astro, not Starlight).
- Styles: `website/src/styles/custom.css`.
- Benchmark pages are generated by `tools/bench/report.py --docs-page`. Do not hand-edit numbers.

## Write a page

Front matter: `title` and `description` (one sentence). Then plain headings (start at `##`; the title is the page title).

- Say what the user can do and what happens, in short sentences. Lead with the task, not the architecture.
- Link between pages with relative links: `[Privacy](../privacy/)`. Never hard-code a host or a base path.
- Use tables for settings, with the default value, and fenced code blocks with a language (`toml`, `sh`, `text`).
- Do not use marketing words, em dashes, or promises. Say what is untested or not built, and link the roadmap.
- Never put a real key, token, or personal path in an example. Use `env:OPENAI_API_KEY` style references.
- Diagrams: use a fenced `mermaid` block (rendered in the browser by `astro-mermaid`, themed for light and dark). Keep labels short; one idea per diagram.
- Starlight asides (`:::note`, `:::caution`) are available. Use them for warnings about safety or data leaving the machine.

## Keep these in step with a code change

| If you changed | Update |
|---|---|
| A config key or default | `reference/configuration.md`, and `shellmate config show/check` text if affected |
| A CLI command or flag | `reference/cli.md` |
| A tool, approval or privacy behaviour | the guide (`exec-tool`, `read-tool`, `man-tool`, `privacy`, `capture`), and `concepts/security-model.md` if an invariant or threat row changes |
| A plugin | `concepts/architecture.md` (plugin table, source layout) and a guide |
| Test or dev workflow | `contributing.md`, `tools/README.md` |
| Something shipped, planned or found missing | `concepts/roadmap.md` (works today, known gaps, planned) |
| Anything a user would notice | `CHANGELOG.md`, under "Unreleased" |
| A slow-start fix or an environment variable | `guides/troubleshooting.md` |

Facts must come from the code or from running the command, not from memory. Check a default in the source before writing it.

## Build and check

```sh
cd website
pnpm install        # first time
pnpm dev            # http://localhost:4321/docs/
pnpm build          # must finish with no errors; this is what CI runs
```

Look at the built page, not only the Markdown: tables, links, and mermaid diagrams are where mistakes hide. A headless browser works for a screenshot (`chrome-headless-shell --virtual-time-budget=8000 --screenshot=...` against `pnpm preview`).

Deployment settings (`SITE`, `BASE`) are described in `website/README.md`. Do not change them as part of a content edit.
